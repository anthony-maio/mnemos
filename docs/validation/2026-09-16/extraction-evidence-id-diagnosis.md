# Extraction evidence ID diagnosis

This is a read-only diagnosis of the preserved 36-observation full-profile lifecycle checkpoint. It does not alter the checkpoint, SQLite databases, frozen source, or prior reports. The method and scalar inventory are preserved in the [diagnostic helper](extraction-evidence-id-artifacts/runner.py.txt) and [report](extraction-evidence-id-artifacts/report.json). To reproduce locally, copy the helper to `.venv/extraction_evidence_diagnosis_v1.py` and run it from this worktree. It requires the original checkpoint and observation databases at the paths recorded in the report; the databases are retained locally and are not included in this archive.

The checkpoint contains 36 observations: 6 complete and 30 partial. Every partial observation has a completed remember job and a pending extract job with `last_error=ValueError`. The recorded exception is `Extraction cited unavailable evidence`. The six complete observations have no recorded maintenance error.

The provider trace contains 55 evidence IDs. SQLite membership checks, performed separately for each observation database, find 25 valid source event IDs and 30 invalid IDs. All 30 invalid IDs are also present in that observation's `memory_chunks.id` set, so they are existing fact IDs verified by database membership. They are not classified as fact IDs from UUID formatting alone. Nineteen observations contain one invalid fact reference plus a valid source event reference. Eleven contain only the invalid support reference. The resulting counts are 30 invalid existing-fact references, 25 valid source-event references, 19 mixed observations, and 11 support-only observations.

For example, `heldout-001:r1` has source event IDs `d53e7dfb65f9b0f1a7092319bc2844d786a41d267a999ee64796ef60d923681d` and `028e3fdf1a44a36d3b1b931b181fbcab8a56dc35a599aaaf6fdd96fb1050da0c`. Its existing fact ID is `6e6fa268-e889-4e60-9206-79b5d78275dc`. The model's support proposal uses that fact ID as both `target_fact_id` and `evidence_ids`. The runtime correctly rejects the latter. A mixed example, `heldout-001:r3`, contains invalid fact reference `a9b7fc87-6778-4d56-a27b-0112d03876c3` and valid source event reference `50c5d19cacb795da0fb66de600278c1c9b2f233905bf7bfff28ca21e97826f62`.

The source path constructs the extraction prompt with source event IDs and existing fact IDs in separate sections. Its output schema names `evidence_ids` and `target_fact_id`, but the prompt does not state explicitly that `evidence_ids` may contain only IDs from `SOURCE EVENTS`. The prompt ambiguity explanation is therefore an inference from the observed fields and responses, not a claim about the model's internal decision.

The runtime guard is correct and should remain strict. A valid source event ID alone does not prove entailment: a support proposal still needs to be justified by the current source events, rather than repeating an existing fact and attaching an arbitrary valid ID. The bounded next step is a new development diagnostic that states `SOURCE EVENTS`-only citations directly, tests corroborating support with separate source and target IDs, tests an unrelated-source negative, correction, and no-durable-fact responses, and retains the invalid-ID case. If that passes, run a fresh heldout matrix with the repaired source provenance. Do not merge these 30 partial observations into that matrix or tune prompts against heldout answers.

The JSON artifact binds the diagnosis to the original checkpoint hash, dataset/config/model/embedding/code hashes, every discovered full-profile SQLite database hash, the observed frozen source path, and serializer repair commit `f3da6487c74b75ead193e028d9783edc10c5dfb5`. It records no raw model response text.
