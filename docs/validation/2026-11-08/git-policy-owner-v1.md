# Resident Git policy owner prototype

The isolated capture worktree now has a serialized, single-root policy owner. It binds the selected Git executable, caller-declared runtime files, the process environment, repository/worktree routing and the discovered configuration dependency closure. Unchanged dependencies are observed again without invoking Git's parser again. Changed roots, file contents or include edges force rediscovery. Configuration and environment contents are retained only in process memory; the probe returns a digest and does not write those values to disk.

Executable observations hash bytes and inspect path/security metadata before and after reading. Windows path stat and open-handle stat report mode and ctime differently; the initial implementation rejected unchanged executables, so its first reuse test failed. The correction compares handle identity, file type, size and mtime, while separately checking all path metadata and security before versus after reading. The original failed run is retained in `.venv/policy-owner-v1.xml`.

The corrected combined owner/dependency/probe/cache suite passed 42 cases in 39.66 seconds, retained in `.venv/policy-owner-v2.xml`. Two additional owner cases then passed with the complete nine-case owner suite in 18.79 seconds, retained in `.venv/policy-owner-v3.xml`. There are 44 distinct passing cases across those runs, not 51 distinct cases. Black and diff checks passed.

Tests demonstrate actual identity reuse with one dependency discovery, invalidation when a missing global file appears, content changes with preserved mtime, newly added include edges and later target creation, runtime-file changes, unreadable observations, unsupported runtime overrides and policy mutation during authoritative lookup. Invalidation tests first establish that an entry was cached, so unconditional fallback cannot make them pass. A malformed global file after caching propagates authoritative Git failure instead of returning stale identity.

The owner is not ready for worker integration. Its explicit `runtime_files` argument must come from a reviewed installation binding: it does not discover a wrapper's child executable or loaded libraries. Tests use an empty additional list or a synthetic file to validate mechanics, not to prove a complete real Git installation dependency set. The Windows selected executable may be a launcher, so declaring only that file would not establish the complete runtime boundary. The next step must bind and verify the actual installation dependencies and then check the owner against that binding. Registry authorization remains outside the cache and must run for every request.

No complete-command timing experiment ran. Repeated file/security observations and hashing have costs that must be included in the bounded complete-path measurement; fewer Git parser calls alone is not a speedup claim. Filesystem observations are not atomic against arbitrary external writers. The cache remains inactive, with no canonical source, installed package, live profile or database changes. Original semantic, timing, delivery and pilot requirements remain open.
