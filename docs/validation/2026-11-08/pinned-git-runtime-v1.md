# Pinned runtime rejection

The inactive policy-owner prototype now accepts a pinned runtime manifest containing the selected Git path, exact SHA256 values for declared runtime files, and bounded directory inventories. Every declared file requires its parent directory to be inventoried. Duplicate/incomplete manifests, malformed hashes and mixed pinned/unpinned arguments are rejected.

When the selected path, file contents or watched directory membership differs, the policy probe returns unavailable and discards its state. Identity lookup then delegates to authoritative Git without publishing a cache entry. Repeated calls do not automatically approve the changed installation. Existing unpinned file-list support remains an experimental testing interface and is not sufficient for integration.

All 16 selected runtime-binding and policy-owner tests passed in 32.12 seconds, retained at `.venv/runtime-binding-v1.xml`. The seven new binding cases cover unchanged reuse; byte replacement with preserved mtime; file addition/removal; a changed executable path with identical bytes; incomplete directory/executable coverage; malformed digests and conflicting API arguments. Mutation cases first establish a populated cache and verify two subsequent authoritative calls without reuse. Black and diff checks passed.

A separate functional check used the seven Git file hashes retained by the previous runtime inspection, plus inventories of their two parent directories. A disposable repository and isolated Git configuration produced two identical resolutions with one authoritative call. All seven file hashes remained unchanged. The exact draft manifest and result are retained under `.venv/pinned-git-runtime-check-v1`. This verifies the mechanism against the observed installation; it does not approve the manifest as a complete dependency closure.

Dynamic loading and DLL search-path coverage still need review before worker integration. Directory inventories cover the declared directories only; they do not establish that every search location or configuration-dependent module has been declared. Updating a binary must require a new verified binding because it may introduce imports absent from the old list. No live Git installation, host setting, memory database or canonical package changed. No timing experiment ran, no speedup is claimed, and the cache remains inactive.
