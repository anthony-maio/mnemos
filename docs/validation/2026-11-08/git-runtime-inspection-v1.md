# Installed Git runtime inspection

The selected local executable is the Git for Windows 2.51.0.windows.1 launcher at `C:/Program Files/Git/cmd/git.EXE`. Its reported exec path is `C:/Program Files/Git/mingw64/libexec/git-core`. The official [wrapper documentation](https://gitforwindows.org/git-wrapper.html) explains the distinction between launcher and native binary. Newer releases can change layout, so a hard-coded path without an installation binding would be insufficient.

A read-only `hash-object --stdin` command was held on its private input pipe long enough to inspect its owned process tree and loaded modules. System/global configuration was isolated to empty temporary files. No object-write flag was used. Closing the input completed the command with exit 0. The launcher, native Git and console-host processes were all absent afterward.

The first inspector assumed exactly two process records and failed its assertion; cleanup still completed. The second retained the process observation before interpreting it and found three processes, including `conhost.exe`. It observed 32 distinct modules overall. Seven files were inside the Git installation: the launcher, `mingw64/bin/git.exe`, `libiconv-2.dll`, `libintl-8.dll`, `libpcre2-8-0.dll`, `libwinpthread-1.dll` and `zlib1.dll`. Those Git files total 6,653,234 bytes.

Static import and delay-import tables of all seven Git files were inspected using pefile 2024.8.26 in a separate temporary tooling environment. All five Git-local imported DLLs appeared in the process observation, including the transitive libintl-to-libiconv edge. File hashes were checked again after inspection. This is evidence for the observed installation and command, not proof of every dynamic load or configuration-dependent path. Windows system modules were recorded separately in the raw module list.

The next owner binding must pin the reviewed executable/runtime hashes and relevant directory membership. It must reject an installation change instead of merely generating a new policy digest and automatically trusting an incomplete old dependency list. A changed native binary can introduce new imports; a newly placed DLL can alter search resolution. Wrapper selection, dynamic loads and search paths remain review obligations before activation. This inspection alone does not approve a runtime manifest or enable the cache.

The adjacent JSON receipt contains the seven file hashes, observed import names, cleanup result and evidence-archive hash. Raw process/module/import records are under `.venv/git-runtime-inspection-v2`; the first failed attempt remains under `.venv/git-runtime-inspection-v1`. The archive includes both retained attempts and the import-inspection helper. The process-inspection commands were executed directly and are preserved in the task transcript, not as archived helper files.

No capture timing experiment, live configuration change, Git installation modification or memory operation occurred. The policy-owner prototype and cache remain inactive. This result establishes which additional runtime files need binding; it does not establish the complete cache contract or latency benefit.
