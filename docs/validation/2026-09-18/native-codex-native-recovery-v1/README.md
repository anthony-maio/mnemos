# Automatic recovery in a fresh native Codex session

Two separate Codex CLI 0.146.0 sessions used the installed c25ed98 wheel and unchanged generated hooks. The first session ran while malformed disposable TOML prevented service startup. Its prompt and final answer remained in the outbox, and SQLite retained zero Codex events. The startup stderr records TOMLDecodeError. The descriptor monitor observed no descriptor in 859 samples, with a maximum gap of 65.1319 ms; sampling cannot rule out a shorter transient.

After the harness explicitly restored the fixture service, a fresh Codex session automatically drained the old queue through its generated hooks. The harness never called replay_outbox. Both native processes exited zero, neither made a model-directed tool call, and the outbox was empty before any subsequent direct maintenance request. The database contained exactly four captured messages: the original two under their original session and turn, plus the new session's prompt and final answer. Each had one evidence link and the expected project, profile, role, and deterministic source identity. The foreign-project control remained intact. Complete-row hashes for facts, events, evidence, and jobs were unchanged after maintenance, service close, restart, and final cleanup.

This closes one native automatic queue-replay observation after startup failure. The service used deterministic lexical embeddings and disabled optional modules. Service restoration was explicit; configured real-provider daemon recovery was not tested. The exact hook that first drained the queue was not traced: SessionStart retrieval or a later capture hook can trigger replay. This does not establish process-kill recovery, concurrent-host behavior, latency percentiles, Desktop or Hermes acceptance, complete host capture, or real-model extraction quality. The earlier punctuation assertion failure and separate direct replay result remain preserved in the preceding startup-outage archive.
