# Local 10,000-fact performance result

The completed performance phase on source `fc72cc2` failed both unchanged latency gates. Warm recall p95 was **4,063.309 ms** against 500 ms across 33 timed queries after three warmup queries. Durable capture p95 was **135.186 ms** against 100 ms across 50 timed events after one warmup event; all 50 acknowledgments were `committed`. The three completed phase artifacts were verified against their coordinator-recorded hashes before copying here.

Embedding p95 was 3,850.212 ms and median was 224.205 ms. The full recall median was 413.250 ms. Actual store-call traces include vector retrieval, lexical retrieval, metadata writes, and returned-row reads without diagnostic follow-up writes. These identify slow components; they do not establish the cause of the multi-second tail or permit dropping outliers.

This uses 10,000 synthetic vectors derived from an observed Nomic embedding, real query embedding calls to local Ollama, and an isolated temporary SQLite database with WAL/FULL durability. All cognition modules were disabled; there were zero cognition calls. Capture used the simple 768-dimensional fixture provider. Semantic quality and actual native-host acceptance are not measured here. The report records local endpoint/model digests and source provenance. GPU readiness is a separate [launch observation](../local-evaluation-launch-v2/README.md), not a per-query GPU-placement trace. The cold synthetic Codex-adapter subprocess took 965.845 ms and is not a real Codex conversation.

A separate network-free diagnostic constructed and closed 12 HTTP clients per arm. Median setup took 199.786 ms with defaults and 182.437 ms with environment handling disabled; profiling attributes most of that time to certificate loading. Current Ollama embedding requests use a fresh `httpx.post` client per call. This is a concrete fixed-overhead finding to investigate. It does not prove that client reuse meets the latency target, explain the entire tail, or justify disabling certificate verification.

The preserved Ollama HTTP log window contains 37 successful embedding requests, matching the seed, three warmup, and 33 timed calls in count. Two server-side durations were 3,496.028 and 3,509.554 ms. These observations show that substantial delays also occurred inside Ollama's request handling during the benchmark window. The log has second-resolution timestamps and no request IDs, so it cannot uniquely pair each entry with a measured query or identify the cause of those delays.

The prior lab-server result remains preserved and is not directly comparable as a code-speedup experiment. Source, machine, endpoint, and execution conditions differ. No threshold, dataset, durability setting, or in-flight evaluation configuration was changed in response to this result.
