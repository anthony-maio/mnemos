# Native pilot startup outage and recovery v1

Freeze this protocol and the amended Codex pilot runner before one native
submission. Retain all original integration results. Use the same persistent
`6d0e5ba6` wheel, exact launcher bytes, private revision-3 hook commands, Codex
and Code Mode binary hashes, `gpt-6-astra` and high reasoning effort. Verify
installed package bytes and every acceptance input before inference.

Use a fresh protected external root. Preserve the launcher's automatic-startup
setting, hook timeouts and actual provider/scheduler configuration. Seed and
complete one explicit retained control through installed MCP, stop its owner
before closing the seed client, and verify descriptor absence and a closed
former service port. Save the original SQLite rows.

Hold the real process lock at the disposable service's ownership-lock path.
Verify that a competing lock cannot acquire it. This deliberately makes normal
automatic startup unavailable; do not disable startup in the host environment,
replace the launcher, patch the client or inject a fake dispatcher. The lock
belongs only to this new test root and must be released in cleanup.

Run one native exec-mode turn within 180 seconds. Keep the previously vetted
one-run hook-trust procedure. Disable Code Mode and expose no MCP tools for
this conversation. The exact prompt and acknowledgement are frozen in
`benchmarks/native_hosts/pilot_outage.py`. Require the pinned native model,
exact submitted prompt, one complete turn and exact acknowledgement. Reject
any native tool call or result. Do not retry inference or repair its output.

Before releasing the lock, require continued descriptor absence, a closed
former port and byte-for-byte-equivalent original SQLite row snapshots. Require
exactly two durable outbox entries matching the native prompt and final reply,
roles, project, profile, session, turn ID and hook source references. Keep the
original outbox and native diagnostics. Hook timeout or degraded diagnostics
must remain visible; successful conversation alone cannot prove capture.

Release the lock. An ordinary fresh installed CLI health request must start
the real service and drain the outbox. Independently inspect both physical raw
events and durable jobs against their exact saved payloads. Run ordinary
maintenance and require completed jobs with two captured-passthrough chunks
whose assertion status remains unknown. No automatically accepted fact is
expected. Preserve the retained explicit control unchanged.

Replay the exact original payloads once through the installed client, then
stop and restart the service again using ordinary CLI health. Require identical
event, job, chunk, evidence and revision rows after replay and the second
restart, an empty outbox, valid SQLite integrity and foreign keys, and the same
physical identities. Keep queued, completed and accepted-fact states separate.

Always release the lock, stop the owned service and remove copied authentication.
Verify all observed owner PIDs and the native PID are absent. Search for remaining
Python service processes naming this exact disposable descriptor; do not stop
unrelated processes. Source authentication, persistent pilot configuration and
all acceptance inputs must remain unchanged. The real pilot must retain no
database or runtime directory.

This is one simulated startup-unavailability scenario with native capture and
real local embedding processing after recovery. It does not prove a provider
outage, mid-transaction crash recovery, repeated-run reliability, ordinary hook
trust approval, extraction quality, pilot days, live activation or publication.
Preserve the first failure and archive sanitized results only.
