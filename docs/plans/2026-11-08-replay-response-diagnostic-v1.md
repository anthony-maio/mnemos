# Replay response scheduling diagnostic

Compare immediate replay notification with notification deferred until after native command exit. Use the unchanged installed queued-capture package and verified native v3 launcher, one resident worker, one real memory service, fresh synthetic storage and deterministic embeddings. No live configuration changes. This is an experimental observer intervention, not a product implementation or acceptance run.

Run five warmups and 50 alternating pairs. Both arms use the native command and the same worker-side timers and receipt writer. Use unique arm/index event identities and session IDs identifying the arm. Set the replay retry interval to 3600 seconds for both arms so the timer does not substitute for the intervention. The startup drain sees an empty queue. Immediate dispatch retains its normal notification; deferred dispatch temporarily suppresses that notification, restoring the method before returning. After command timing ends, an authenticated diagnostic operation wakes replay. Require queue drain and completed persistence before the next sample.

Measure full command completion, service submit, dispatch and within-sample before/after-dispatch intervals. Preserve every observation, correlate receipts and event IDs, and verify all jobs complete. Freeze helper, wrapper, artifact identities and schedule before launch. Compare the measured after-dispatch intervals to test whether replay contributes to response delay. Other OS scheduling and observation overhead remain; do not claim the experiment proves a general latency target or directly deploy the diagnostic endpoint.
