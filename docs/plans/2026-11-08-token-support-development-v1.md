# Binary source-witness support development

This candidate replaces generated probability JSON with one scored token per fact/source witness. It is a different decision mechanism from the closed contrast, sparse-choice, named-choice, and discriminative experiments. Their inputs, outputs, and failures remain unchanged. Do not reuse those cohorts to claim fresh quality.

The development selector receives the existing immutable scoped snapshot. Every request includes the literal query, explicit reference date, and the complete eligible comparison cohort with all retained source excerpts. Its target identifies exactly one candidate and one of that candidate's own sources. The shared data prefix precedes the target so a provider may reuse that prefix without dropping comparison evidence. No candidate prefilter or early positive short-circuit is allowed.

The prompt asks for A only when the designated source supports the complete qualified fact, the fact answers the requested subject/relation/time, and source-backed comparison evidence leaves no unresolved contradiction or supersession. Otherwise it asks for B. The JSON is explicitly untrusted data. This instruction is a hypothesis to evaluate, not proof that the model follows it.

The fixed prospective rule accepts a source witness only when the generated label is A and its reported, unrenormalized token probability is at least 0.9. Both A and B must appear in the returned alternative scores. Missing or malformed scores are unavailable, never zero probability or successful abstention. The 0.9 value is an uncalibrated candidate rule selected before semantic evaluation; it is not equivalent to the earlier 0.8 generated self-rating threshold. Do not adjust it after seeing this experiment's results.

A fact is selected when at least one of its own source requests passes. Every own source is still assessed, and each request sees the entire cohort. Preserve all selected witness IDs in source order. A later provider failure invalidates the composition even if an earlier witness passed. The existing composition enforces membership, evidence, and revision checks around provider work and owns the shared timeout. The new selector does not activate a production retrieval path.

Preflight all requests before the first call. The complete request set is limited to 32 requests and 64,000 UTF-8 prompt bytes. Exceeding either limit is an operational failure; never truncate the cohort. The provider must separately verify actual prompt token counts before inference and reject over-context inputs without truncation. Keep thinking disabled and one output token. Preserve complete prompts, responses, token counts, per-request elapsed times, and whole-query times, including all failures and cleanup.

Before inference, author a separate development cohort covering direct support, absent answers, temporal qualifications, proposals, quoted claims, source contradictions, unsupported peer claims, and source instructions. Separate gold labels from runtime inputs. Freeze the cohort, labels, prompt builder, decoder, rule, request order, source/evidence bindings, model assets, Ollama executable, runner executable, loaded runtime libraries, dependencies, and provider settings. Do not infer historical runner hashes from current files.

Run a bounded development screen once under that freeze. Report answerable recall, critical-fact retention, selected-fact precision, correct abstention, operational failures, and whole-query support time. Repetitions are not new semantic cases. Any support-only timing excludes retrieval and cannot pass the complete 500 ms recall gate. The original requirements remain 95% precision and critical-fact retention, 90% recall and abstention, 500 ms complete warm retrieval at 10,000 facts, and the separate capture and pilot requirements.

Model-free tests establish request construction, witness binding, scope exclusion, fixed-rule boundaries, budget rejection before calls, snapshot invalidation, cancellation propagation, and provider failures. They do not establish semantic quality. Only after development passes should a separately authored fresh acceptance cohort be opened. No pilot or release promotion follows from these tests.
